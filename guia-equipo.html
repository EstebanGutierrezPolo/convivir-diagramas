El proyecto

Convivir, en una frase

Una plataforma web para administrar un conjunto residencial: quién vive en cada apartamento, quién puede entrar, quién debe cuánto y quién reservó el salón.

A

Administrador

Inmuebles, personas, cobros, pagos, reservas y reportes.

V

Vigilante

Registra quién entra y sale, personas y vehículos.

R

Residente

Autoriza visitas, paga, reserva zonas y reporta novedades.

C

Consejo

Consulta la cartera y la auditoría.

La idea central: toda la información se ancla al inmueble, no a la persona. Si cambia el dueño o el arrendatario, la historia del apartamento no se pierde.

Tecnologías

Cómo se hablan: API REST y JSON

El frontend le hace pedidos al backend por internet, como cuando escribes una dirección en el navegador. Esa lista de pedidos posibles es la API.

El frontend pregunta

GET /api/estado

GET es "dame". También hay POST (crea), PUT o PATCH (cambia) y DELETE (borra).

El backend responde en JSON

{ "aplicacion": "ok",
  "baseDeDatos": "ok" }

JSON es un formato de texto con pares nombre y valor, fácil de leer para personas y programas.

Ese pedido existe hoy: es lo único que ya hace nuestro backend. Confirma que la aplicación responde y que llega a la base de datos.
Herramientas

Git: el historial de versiones

Git guarda fotos de una carpeta a lo largo del tiempo. Cada foto se llama commit y lleva un mensaje que dice qué cambió. Es como el control de cambios de Word, pero para todo un proyecto.

Ejemplo de un historial, de izquierda a derecha:

a1f3esqueleto del proyecto
b7c2diagramas UML y visor
c9e4sistema de diseño
d2a8vistas de la aplicación

Se puede volver atrás

Si algo se daña, regresamos a una foto anterior.

Se sabe quién y por qué

Cada cambio dice su autor, su fecha y su mensaje.

Varios a la vez

Cada uno trabaja en su copia y luego se juntan los cambios.

Herramientas

Docker: cada pieza en su caja

Un contenedor es como una lonchera: trae adentro todo lo que la pieza necesita para funcionar (su Java, su Node, su base de datos). Así corre igual en cualquier computador.

Imagen

La receta: dice qué va dentro de la caja. Se escribe en un archivo llamado Dockerfile.

Contenedor

La caja ya armada y funcionando, hecha a partir de la imagen.

Docker Compose

Levanta varios contenedores juntos con un solo comando, según el archivo docker-compose.yml.

Volumen

Un espacio donde la base de datos guarda sus datos, para que no se borren al apagar.

Por qué lo usamos: nadie tiene que instalar Java, Maven ni PostgreSQL en su PC. Solo Docker Desktop. Y se acaba el "en mi computador sí funcionaba".

Paso a paso

Cómo tenerlo funcionando en tu PC

1. Instala dos programas

Git y Docker Desktop. Abre Docker Desktop y espera a que diga que está corriendo.

2. Arma la carpeta

Crea una carpeta convivir con docker-compose.yml y .env.example, y clona ahí los tres repositorios.

# 2. Dentro de la carpeta convivir
> git clone https://github.com/EstebanGutierrezPolo/convivir-frontend.git frontend
> git clone https://github.com/EstebanGutierrezPolo/convivir-backend.git backend
> git clone https://github.com/EstebanGutierrezPolo/convivir-diagramas.git diagramas
# 3. Copia .env.example como .env y pon tu propia contraseña
# 4. Levanta todo (la primera vez tarda unos minutos)
> docker compose up -d --build
# 5. Abre http://localhost:3000 en el navegador
# Para apagarlo
> docker compose down
Ojo: docker-compose.yml, .env.example y el README de la carpeta raíz todavía no están en un repositorio. Por ahora se comparten aparte; pídeselos a Esteban.
Diseño

Los diagramas son la fuente de verdad

Los diagramas UML están escritos como texto en Mermaid, así se guardan en Git como el código. Tienen su propio visor y editor.

> cd diagramas
> npm install # solo la primera vez; necesita Node 22 o superior
> npm start
# Abre http://localhost:4000

Diagramas

Casos de uso, clases, componentes, despliegue y uno de secuencia por caso de uso. Se editan y se descargan en SVG para Word.

Sistema de diseño

Colores, letras y componentes que siguen todas las pantallas, en tema claro y oscuro.

Vistas

Las pantallas definitivas de la aplicación, una por caso de uso, para cada tipo de usuario.

Regla del proyecto: el diagrama es el código. Cada clase del diagrama existe en Java con el mismo nombre, atributos y métodos. Si el código necesita algo distinto, primero se cambia el diagrama.

Siguientes pasos

Qué sigue y cómo pueden ayudar

1. Revisar los diagramas

Cada uno toma unos casos de uso y revisa su diagrama de casos de uso y de secuencia en el visor. Lo que no cuadre con el documento v1.2, se anota.

2. Cerrar las decisiones abiertas

Están en la pestaña Proyecto del visor. Ejemplo: ¿un apartamento puede tener varios propietarios?

3. Programar caso por caso

Cada caso de uso se programa siguiendo su diagrama de secuencia: primero las clases del dominio, luego la API y luego la pantalla.

4. Escribir la metodología

Cómo trabajamos, cómo repartimos y cómo revisamos. También la califican.

Lo que califican: los diagramas, la aplicación funcionando, la metodología y cómo se llevaron las relaciones del diagrama al código.
